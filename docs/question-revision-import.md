# Question revision import

The checked-in research document `docs/research/question-revisions-20261010.json` is the source for this bounded nine-question update. The importer validates its pinned SHA-256, schema, baseline commit, reviewed qid set, provenance and `NOT_RUN` status before planning changes.

Run `npm run question:revisions` for the default dry-run. It validates the source and current baseline, then reports the planned canonical and generated files without writing. Apply only with `npm run question:revisions -- --apply`. The apply updates the nine named master questions and their chapter titles, then regenerates the repository's existing question, topic and content-manifest indexes. Unknown or duplicate qids, unexpected fields, blank content, changed source hash, mismatched question baselines or a partially applied batch fail closed. A repeated apply reports `already-applied` and does not replace later edits.

Apply takes an exclusive `.question-revisions.lock` in the checkout before reading any content. The lock covers source validation, baseline preparation, candidate generation and install. It rejects another importer instead of waiting. The importer records hashes of all five canonical/generated files it reads and checks them again immediately before install and before each replacement, so an intervening edit is preserved and the batch aborts. Other tools should honor the same checkout lock; the hash checks also detect ordinary edits that do not.

The importer generates all candidate files in a temporary stage directory, copies the original files into a backup area, and installs each candidate by rename. If an install operation fails, it restores files already moved. This is a recoverable multi-file install, not a filesystem-wide atomic transaction. If rollback itself fails, the stage directory and backups are retained and its path is included in the error. Inspect those backups before manual recovery. A hard process termination can leave both a stage directory and lock behind; verify no importer is running, inspect the lock metadata and staged backups, then remove a stale lock manually. The tool deliberately does not guess whether a lock is stale or delete it automatically.
